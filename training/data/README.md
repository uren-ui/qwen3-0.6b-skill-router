# 训练数据说明

三个字段的 JSONL，一行一条：

```json
{
  "task":     "给我画下雨天的街道，存到 D:\\ai-lab\\pelican.svg",
  "manifest": "可用技能：\n- switch_model（成功率1.0，中位7.98s）：……\n- write_svg（成功率0.5……）：……",
  "output":   "{\"action\":\"call\",\"skill\":\"write_svg\",\"params\":{\"spec\":\"下雨天的街道\",\"path\":\"D:\\\\ai-lab\\\\pelican.svg\"}}"
}
```

| 字段 | 说明 |
|---|---|
| `task` | 用户原话，一行。平均 23.6 字（训练集），最短 2 字，最长 56 字 |
| `manifest` | **运行时注入的技能清单**，纯文本。平均 1274 字。每个技能带：名称、成功率、中位耗时、坑（如果有）、参数与边界 |
| `output` | 目标输出，**是一个 JSON 字符串**（不是嵌套对象）——保持和推理时逐字符比对的口径一致 |

## 为什么 manifest 是字符串而不是结构化数组

因为推理时它就是塞进 user message 的一段文本。训练和推理必须完全同构，任何一处做了"美化"（比如转成 JSON、调整缩进）都会让模型学到训练里不存在的格式。

## 数据怎么来的

程序合成的，不是人工标注：

1. 从技能注册表里取出每个技能的**参数 schema 和边界描述**
2. 按模板 + 同义替换生成任务句式（"给我画 X 存到 Y" / "把模型切到 X" / "看看现在哪个模型在线" …）
3. 每条任务配一份**当时真实的 manifest**（含从执行记录统计出的成功率和中位耗时）
4. 用规则模板生成 `output`（不是用大模型标注，避免把大模型的幻觉灌进小模型）

代价是句式高度模板化——这也是这版模型最大的短板。真实用户说话一旦绕弯（"我想搞个下雨街道的图，放 D 盘 ai-lab 下面叫 pelican.svg"），容易错判成 `ask`。

## 复用注意

- **不要把 manifest 写死进 system prompt**。这套数据的全部价值在于"清单随任务变化"，写死会让模型退化成背表。
- 换技能池必须重新生成数据重训，零样本迁移能力基本为零。
- 数据里包含 Windows 路径（`D:\ai-lab\...`），只是任务文本的一部分，不含个人信息、不含第三方数据。
