# 评测说明

## 口径

指标是**输出 JSON 的精确匹配**（exact match），不是字段级 F1，也不是语义相似度。

```python
got = decode(model.generate(...)).strip()
ok  = got.replace(' ', '') == gold.replace(' ', '')      # 去掉所有空格后逐字符
```

为什么这么严：下游是执行器，不是人。技能名写错一个字母 → 找不到技能；参数名写错 → 整个调用失败；多一句解释 → JSON 解析崩。这里没有"差不多对"的余地。

但**空格不卡**：模型习惯输出 `"action": "call"` 这种带空格的写法，语义完全一致。所以口径是"去掉所有空格后逐字符比对"——key 名、值的字符串本身一个字节都不能差，缩进和空格不管。

## 测试集

`training/data/dev_eval_60.jsonl` = `dev_mix.jsonl` 的前 60 条，和 `train_judge.py` 里 `evaluate(..., limit=60)` 取的是同一批。

| action | 条数 |
|---|---|
| `call` | 约 36 |
| `refuse` | 约 14 |
| `ask` | 约 10 |

（粗略分布；`dev_mix` 全量 312 条的分布是 call 190 / refuse 70 / ask 52。）

## 结果（训练过程中逐 epoch 记录）

| epoch | 平均 loss | 验证集精确匹配 | 备注 |
|---|---|---|---|
| 1 | 0.0526 | 58/60 = 97% | 已经基本学会格式 |
| 2 | 0.0030 | 59/60 = 98% | 错的 1 条一直错 |
| 3 | 0.0012 | **60/60 = 100%** | 发布版保存于此刻 |

结论：**格式学习在第一个 epoch 就完成了，后面两个 epoch 学的是"这批数据的细节"，不是能力。**

## 怎么看待这个 100%

必须打三个折：

1. **同分布**。验证集和训练集出自同一套合成流程，句式模板一致。跨句式测试（改口语、加冗余从句、混英文）没有覆盖，实际使用会掉。
2. **只有 60 条**。1 条 = 1.7 个百分点。60 条上的 100% 只能说明"没崩"，不能说明"很好"。
3. **loss 掉到 0.0012**。这是背格式的典型信号。要验证泛化，需要一批**人工手写、且刻意打乱句式**的测试集——本仓库没有，属于已知缺口。

## 已知的错法（实测收集）

| 输入 | 期望 | 实际 | 为什么会错 |
|---|---|---|---|
| "帮我看看显卡还剩多少" | `refuse`（清单里没有查显存的技能） | `call: model_status` | 语义近邻，0.6B 分不清"查模型"和"查显卡" |
| "画只猫，随便放哪" | `ask`（缺 path） | `call: generate_image`（params 里 path 编了一个） | 缺参数时会硬编，这是数据里 `ask` 样本太少（7.7%）导致 |
| 组合任务串三个诉求 | `call: combo:c11` | `call: write_svg` + 丢掉后两个 | 落在训练里没见过的组合上 |

## 复现评测

```bash
python examples/infer.py --eval       # 需要 examples/infer.py 里实现评测分支
```

或直接用训练脚本里的 `evaluate()`——它每 epoch 会自动跑一遍并打印 `>> 验证集精确匹配 X/Y`。

## 建议的下一步

如果要把这个模型往外推，优先补这三块（按性价比排序）：

1. **`ask` 样本扩到 30% 以上**。现在的模型太爱硬编参数，这是实际使用中最早暴露的问题。
2. **人工手写 200 条对抗测试集**（口语化、错别字、英文混输、多诉求、缺参数），单独报一次分。
3. **技能池扩到 15+ 个后重训**，看清单变长时的准确率衰减——这是判断"能不能当通用路由器"的关键实验。
